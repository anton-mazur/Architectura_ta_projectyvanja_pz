# Завдання 2. Компонентна діаграма (UML Component Diagram) - 3-рівнева архітектура

## 1. Архітектурний підхід: Багаторівнева клієнт-серверна архітектура (3-Tier Layered Architecture)

Для системи бронювання квитків обрано **трьохрівневу архітектуру (3-Tier Layered Architecture)** за класичною моделлю «клієнт-сервер».

Головною перевагою даного архітектурного підходу є дотримання фундаментального принципу інженерії програмного забезпечення — **розділення обов'язків (Separation of Concerns, SoC)**. Кожен шар системи вирішує виключно своє коло завдань і взаємодіє із сусідніми рівнями через чітко специфіковані абстрактні інтерфейси (REST API, Repository Contracts).

Це забезпечує:
- **Модульність та низьку зв'язність (Low Coupling):** Зміна користувацького інтерфейсу або заміна СУБД не зачіпає правила бізнес-логіки.
- **Масштабованість:** Шар сервісів не зберігає сесійного стану (stateless), що дозволяє масштабувати бекенд горизонтально під час пікових навантажень (наприклад, старт продажів квитків на популярний концерт).
- **Безпеку:** Клієнти не мають прямого доступу до бази даних; усі операції валідуються та авторизуються на рівні бізнес-сервісів.

## 2. Визначення та роль 3-х основних шарів

### 1) Presentation Layer (Шар представлення / UI)
- **Компоненти:** `Web Application (React / Next.js SPA)`, `Mobile Application (iOS / Android)`, `Admin Dashboard UI`.
- **Роль:** Відповідає виключно за рендеринг інтерфейсу, відображення інтерактивної схеми залу з вільними/зайнятими місцями, приймання введення від користувача та валідацію форм на боці клієнта.
- **Взаємодія:** Надсилає асинхронні HTTPS/JSON-запити до шару бізнес-логіки через публічний інтерфейс `REST API / JSON Gateway`.

### 2) Business Logic Layer (Шар бізнес-логіки / Сервіси)
- **Компоненти:** 
  - `Booking Service` — керує життєвим циклом бронювання, формує тимчасові блоки на місця, запускає 15-хвилинні таймаути;
  - `Event & Catalog Service` — забезпечує вибірку розкладу подій, конфігурацію майданчиків та цінові сітки;
  - `Payment Service` — управляє взаємодією з банківським еквайрингом (Stripe / LiqPay / Fondy), обробляє webhook-сповіщення про успіх чи відхилення платежів;
  - `Ticket & Notification Service` — генерує PDF-квитки з унікальними QR-кодами та ініціює відправку листів/SMS;
  - `Auth & User Service` — відповідає за реєстрацію, автентифікацію та видачу JWT-токенів безпеки.
- **Роль:** Реалізує всі ключові бізнес-правила системи, гарантує недопущення «подвійного бронювання» одного місця (конкурентні запити), розраховує знижки та керує транзакційними сценаріями.

### 3) Data Access Layer (Шар доступу до даних / Репозиторії)
- **Компоненти:** `Booking Repository`, `Event Repository`, `User Repository`, `ORM & Query Engine (Entity Framework / Hibernate)`.
- **Роль:** Абстрагує бізнес-логіку від деталей взаємодії з реляційною базою даних. Надає інтерфейс `IRepo` для виконання атомарних CRUD-операцій, контролює блокування записів (pessimistic / optimistic locking) при резервуванні місць.
- **Взаємодія з БД:** Використовує пул з'єднань (Connection Pool) та виконує SQL-запити до `PostgreSQL Database`.

### Зовнішні інтеграції (External Services):
- `Payment Gateway` (LiqPay / Stripe) — безпечне списання безготівкових коштів з банківських карток;
- `Email & SMS Gateway` (SendGrid / TurboSMS) — доставка згенерованих квитків та сервісних повідомлень.

## 3. Взаємодія між шарами (Dependency Flow)

Залежності мають суворо спрямований зверху вниз характер:
$$\text{Presentation Layer} \xrightarrow{\ll\text{use}\gg} \text{Business Logic Layer} \xrightarrow{\ll\text{use}\gg} \text{Data Access Layer} \xrightarrow{\text{SQL}} \text{Database}$$

1. Клієнтський застосунок (`WebApp` / `MobileApp`) формує HTTP-запит і звертається до точки входу `IApi`.
2. Шар представлення передає запит у відповідний сервіс (наприклад, `BookingService`).
3. `BookingService` взаємодіє з суміжними сервісами (`EventService` для перевірки статусу залу, `PaymentService` для старту транзакції).
4. Сервіси бізнес-логіки використовують об'єкти передачі даних (DTO) і звертаються до `IRepo`.
5. Репозиторії за допомогою ORM виконують транзакційне оновлення бази даних `PostgreSQL`.
6. Результат обробки повертається зворотним шляхом у вигляді JSON-відповіді для відображення клієнту.
