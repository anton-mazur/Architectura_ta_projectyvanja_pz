# Завдання 5. Архітектурний опис системи (Система бронювання квитків)

## 1. Мета проєкту
Метою розробки системи є створення масштабованої, відмовостійкої цифрової платформи для автоматизації процесу онлайн-продажу квитків на масові культурні та спортивні заходи (концерти, театральні вистави, кінопокази).

Система вирішує ключові задачі галузі:
- Забезпечення інтерактивної візуалізації схем глядацьких залів із відображенням статусу доступності окремих місць у реальному часі.
- Запобігання колізіям та подвійному бронюванню місць (конкурентні транзакції при пікових навантаженнях).
- Автоматизація часових лімітів (15-хвилинний таймаут на оплату з автозвільненням місць).
- Безпечна інтеграція з міжнародними та національними платіжними провайдерами (Stripe, LiqPay, Apple Pay).
- Генерація захищених електронних квитків у форматі PDF з унікальними QR-кодами для миттєвої валідації контролерами на вході.

## 2. Тип та обґрунтування архітектурного підходу

Для проєкту обрано **трьохрівневу клієнт-серверну архітектуру (3-Tier Layered Architecture)**:

```
+-------------------------------------------------------------+
|               Presentation Layer (UI / Клієнти)            |
|         [Web React App]  [Mobile iOS/Android]  [Admin UI]   |
+------------------------------+------------------------------+
                               | HTTPS / REST API (JSON)
+------------------------------v------------------------------+
|            Business Logic Layer (Сервіси та правила)        |
|  [BookingService] [EventService] [PaymentService] [Ticket]  |
+------------------------------+------------------------------+
                               | DTO / Repository Interfaces
+------------------------------v------------------------------+
|           Data Access Layer (Абстракція доступу до даних)    |
|       [BookingRepo]  [EventRepo]  [UserRepo]  [ORM]         |
+------------------------------+------------------------------+
                               | SQL / Connection Pool
+------------------------------v------------------------------+
|               PostgreSQL Relational Database                 |
+-------------------------------------------------------------+
```

### Чому обрано цей підхід:
1. **Розділення обов'язків (Separation of Concerns):** Користувацький інтерфейс, правила обробки бронювань та збереження даних ізольовані один від одного. Редизайн клієнта або зміна платформи не впливають на бекенд.
2. **Горизонтальне масштабування:** Шар сервісів є stateless (не зберігає стану клієнтських сесій локально). Це дозволяє запускати кілька екземплярів бекенда за балансувальником навантаження (Nginx) для обслуговування десятків тисяч користувачів у момент старту продажів.
3. **Безпека та цілісність:** Прямий доступ до бази даних із боку клієнта повністю унеможливлений. Всі запити проходять крізь рівень бізнес-валідації, захист від ін'єкцій та аутентифікацію JWT.

## 3. Основні компоненти та підсистеми

1. **Шар представлення (Presentation Layer):**
   - Клієнтські застосунки для покупців (Web SPA на React, мобільний клієнт на Flutter);
   - Веб-панель адміністратора та мобільний сканер квитків для контролерів на турнікетах.
2. **Шар бізнес-логіки (Business Logic Layer):**
   - `BookingService` — координація резервацій, контроль статусів, керування таймерами;
   - `EventService` — управління подіями, категоріями квитків та схемами залів;
   - `PaymentService` — взаємодія з платіжним еквайрингом (Stripe / LiqPay), обробка webhooks;
   - `TicketService` — криптографічна генерація QR-кодів і збирання PDF-файлів квитків;
   - `AuthService` — управління користувачами, хешування паролів (BCrypt) та генерація JWT.
3. **Шар доступу до даних (Data Access Layer):**
   - Патерн *Repository* для абстракції SQL-запитів;
   - ORM (Entity Framework / Hibernate) для мапінгу сутностей;
   - Атомарні транзакції з блокуванням рядків (`SELECT ... FOR UPDATE` або `UPDATE ... WHERE status='FREE'`) для гарантії ізоляції транзакцій.
4. **База даних:**
   - Реляційна СУБД `PostgreSQL`, що підтримує транзакційні стандарти ACID.
